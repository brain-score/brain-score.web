## Initial confirmed blockers

1. **Database imports do not power the page.**
   `benchmarks/model_metadata/repository.py` reads and caches the CSV catalog;
   `build_model_card_metadata()` in `benchmarks/views/model.py` calls that reader.
   Implement a database reader returning the existing card context. Keep the
   submission fallback for models without curated records.

2. **The importer can delete everything on an empty catalog.**
   `import_model_metadata.py` builds an empty `Q()` and calls `filter(...).delete()`
   when `models.csv` contains no records. Reject empty input before entering the
   mutation path, including with `--wipe`. Ordinary imports must preserve records
   outside the imported keys. Existing transaction handling is useful and should
   remain.

3. **Seven populated CSV columns are not persisted.**

   | Column | Models with a value |
   | --- | ---: |
   | training_objective | 60 |
   | loss_function | 59 |
   | learning_rate | 17 |
   | batch_size | 22 |
   | input_format | 72 |
   | output_format | 59 |
   | tokenizer | 1 |

   Add fields and importer mappings before switching readers. Preserve descriptive
   values as text where the workbook contains prose or schedules. Verify every
   existing CSV column and every child table, not just these seven fields.

4. **The bundled data exceeds one PostgreSQL column limit.**
   The `pixels` test-dataset name is 202 characters, while
   `ModelMetadataDataset.dataset_name` is a `CharField(max_length=200)`.
   This exceeds PostgreSQL's varchar limit. Prefer splitting the long explanatory
   text into `description` and using a concise dataset name, or deliberately widen
   the schema. Do not truncate silently. Validate lengths before modifying data.

5. **The converter and reader disagree on confidence values.**
   `scripts/build_model_metadata_catalog.py` emits `inferred` and `low`, including
   from workbook colors. The bundled assertions and card reader use `probable`
   and `uncertain`. Regeneration would omit corresponding badges and named counts.
   Adopt one vocabulary across conversion, validation, storage, and rendering.
   Reject unknown statuses. A nonempty, uncolored cell currently defaults to
   `verified`; this needs an explicit curation policy rather than an implicit
   verification claim.

6. **CI is red and metadata-specific coverage is absent.**
   Jenkins build 663 ran 81 tests: one failure and two skips. The failure is
   `TestWebsitePages.test_model_page`, at its exact-class lookup for `h3#scores`.
   The template adds `mc-title`, so update the test to use semantic selectors.
   Its later sidebar checks also depend on old class strings and capitalization.
   Preserve the assertions about real content while making selectors resilient.
   The existing database test runner skips database setup and teardown, so this
   CI run does not establish clean-database migration safety.

## Database implementation

- Retain the six-table design. Keep workbook/CSV files as reviewed import inputs;
  make PostgreSQL the website's metadata source of truth.
- Add a follow-up migration after the existing merge migration. Preserve both
  existing 0027 names and their dependencies.
- Validate required headers, nonempty identifiers, field types, lengths, allowed
  statuses/roles/categories, duplicate child keys, and orphan rows before writes.
  Add a dry-run mode that reports proposed changes without mutating the database.
- Define one case-insensitive identifier policy for imports, lookup, and lineage;
  reject ambiguous duplicates and preserve distinct checkpoint suffixes.
- Prefer updating records by their natural key and replacing their imported child
  rows within a transaction, retaining stable record IDs on repeated imports.
- Fetch related rows in batches. Avoid both per-field queries and a permanent
  per-worker cache that cannot observe imports. Start without such a cache; add
  versioned invalidation only if measurement warrants caching.
- Keep existing submission fallback behavior for absent records. Do not silently
  hide database outages behind CSV fallback.
- Resolve lineage links only to public models in the same domain, with consistent
  casing. Also consider bases that exist on the site but lack a curated record:
  the current `lineage_identifiers()` excludes those ancestors.
- Validate catalog identifiers against a public-model export before deployment.
  Report unmatched entries without merging similarly named checkpoint variants.

## Superseded UI simplification proposal

Use the current page structure and styling system. A full redesign increases
scope; fixing only the listed bugs leaves the duplicate facts and sparse cards.
The recommended middle option is a compact overview with expandable details.

- **Header:** model name, paper/source links, and Compare. Put concise architecture,
  parameter count, input size, and supervision facts in one place. Long narrative
  descriptions belong in details rather than header chips.
- **Content order:** compact overview, benchmark scores and trends, then detailed
  metadata. Keep existing usage instructions easy to find. Metadata should not
  push the model's benchmark results far down the page.
- **Details:** expandable Training and data, Intended use and limitations, and
  Evaluation and interface sections. Show populated fields initially; offer a
  secondary way to inspect undocumented fields. Entirely empty sections get one
  short summary rather than a grid of empty placeholders.
- **Source wording:** distinguish Curated metadata from Submission metadata.
  Missing fields in a curated record must not imply the model was never curated.
  Missing tokenizer information must not automatically mean Not applicable.
- **Sidebar:** keep layer commitment, visual angle, and useful lineage. Replace
  the large provenance card with a compact summary and expandable source details.
  Keep confidence and completeness distinct; their current denominators differ
  between curated and submission records.
- **Controls:** remove disabled Edit buttons and the public Schema v2.0 badge.
  Use native details/summary or buttons with `aria-expanded` and `aria-controls`.
  Make confidence explanations available by keyboard and touch, with text labels.
- **Lineage:** ensure `[hidden]` rows remain hidden despite `display: flex`; test
  both expansion and recollapse. Forty of the 78 catalog cards have more than
  three related variants, so this is broadly visible.
- **Layout:** allow long identifiers and URLs to wrap without widening the page.
  Check the full page at desktop, tablet, and narrow mobile sizes, including
  sidebar stacking and comparison navigation.
- **Filter links:** ensure the visible curated value agrees with the filter
  target; current links use legacy metadata even when the displayed fact is
  curated. Omit misleading links when the vocabularies cannot be reconciled.

## Acceptance checks and rollout

1. Test conversion status normalization, empty and malformed imports, transaction
   rollback, repeated imports, partial imports, case collisions, and child order.
2. Import the bundled catalog into disposable PostgreSQL and compare every scalar
   and child value with the CSV input. Current expected counts are 78 models,
   225 datasets, 520 intended-use rows, 138 contributors, 71 relationships, and
   2,418 assertions. Counts alone do not prove value parity.
3. Validate a fresh migration chain and upgrade paths from both 0027 histories.
   Run with the supported Django 4.1 dependency range and a test runner that
   actually creates and migrates the disposable database.
4. Compare CSV and database card contexts for the bundled models, then exercise
   curated, partial, fallback, and empty cards. Include mixed-case identifiers,
   distinct checkpoints, cycles, unresolved ancestors, and private-link exclusion.
5. Browser-check complete pages for `resnet-50-robust`,
   `vit_base_patch16_clip_224:openai_ft_in1k`, the fallback checkpoint
   `vit_base_patch16_clip_224:openai_ft_in12k_in1k`, and a model without usable
   submission metadata. Include a long identifier and more than three relatives.
6. Re-run existing page and comparison tests plus focused keyboard/mobile checks.
7. In staging: apply schema migrations, dry-run the import, import atomically,
   verify parity, then enable database reads. Record the input revision and counts.
   Keep the prior application release and a metadata backup available for rollback.
   Repeat the documented sequence for production only after staging passes.

Broader model coverage, a metadata editor, and exhaustive primary-source curation
can follow this PR. Before merge, preserve uncertainty honestly and avoid implying
that `curation_workbook` is a field-level primary reference: all 2,418 bundled
assertions currently use that generic source. Provide adequate storage for real
references; the current 100-character source column is too restrictive for many
URLs. Comprehensive source collection is separate from safe migration.
